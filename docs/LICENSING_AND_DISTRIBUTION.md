# Лицензия, регистрация и публикация WinRepair

> Это практическое руководство, а не юридическая консультация. Текст лицензии и вопросы авторских прав лучше согласовать с юристом в вашей стране.

## 1. «Регистрация продукта» — это три разные вещи
| Что | Зачем | Обязательно? |
|---|---|---|
| **Лицензия** (файл `LICENSE.txt`) | Правовые условия: кто и как может пользоваться, чего вы не гарантируете | Да, без неё пользователи формально не имеют прав на использование |
| **Регистрация авторских прав** | Доказательство авторства и даты создания | Нет: право возникает с момента создания. Помогает в споре (депозит исходников у нотариуса, в нац. ведомстве по ИС, либо хотя бы подписанный тег в git + архив с датой) |
| **Активация / лицензионный ключ** | Техническое ограничение функций (платные редакции, срок) | Нет. Нужна только если вы продаёте |

Совет: на этапе 1.0 выпускайте как **бесплатную (freeware) версию с EULA** или как открытый код. Систему ключей добавляйте, когда появятся первые пользователи и решение о цене.

## 2. Какую лицензию выбрать
| Вариант | Суть | Когда подходит |
|---|---|---|
| **MIT / Apache-2.0** | Любой может использовать, менять, продавать; сохраняется упоминание автора (Apache-2.0 даёт ещё и патентную защиту) | Хотите максимальное распространение и доверие, исходники открыты |
| **GPL-3.0** | Производные работы тоже должны быть открыты | Хотите, чтобы доработки возвращались сообществу |
| **Freeware EULA** (закрытый код) | Бесплатно для использования, нельзя менять/продавать/распространять отдельно без разрешения | Хотите контролировать продукт, исходники не публикуете |
| **Коммерческая EULA** | Платная лицензия: на мастера / на организацию / на устройство | Продаёте утилиту сервисным центрам |

Что нужно вписать в `LICENSE.txt`: год, правообладатель (ваше имя или организация), выбранный текст, отказ от гарантий («как есть»), ограничение ответственности (потеря данных при ремонте). Шаблон лежит в корне проекта.

**Проверьте до публикации:** права на `bsod-codes.json` (откуда взяты данные), а также что Sergei Strelec / сторонние утилиты вы не включаете в свой пакет без разрешения их авторов (в `Tools\` кладите только то, на что есть право).

## 3. Git и GitHub: куда что класть
Репозиторий уже создан локально (папка `.git` в архиве), в нём история коммитов и тег `v1.0.0-rc1`.

Структура корня репозитория (GitHub сам находит эти файлы и показывает вкладки):
```
LICENSE.txt (или LICENSE)   лицензия — вкладка «License»
README.md                   описание — главная страница
SECURITY.md                 как сообщить об уязвимости — вкладка «Security»
CHANGELOG.md                история версий
PRIVACY.md  THIRD_PARTY_NOTICES.md
docs/  src/  res/  Playbooks/  lang/  tools/  tests/
```
**Не коммитьте:** `.pfx`, закрытые ключи, пароли (они уже в `.gitignore`: `*.pfx`, `*.snk`), готовые `.exe` (их место — «Releases», а не история кода).

Публикация (однократно):
1. Создайте аккаунт на github.com и **приватный** репозиторий `WinRepair` (позже можно сделать публичным).
2. В папке проекта:
   ```
   git remote add origin https://github.com/<ваш-логин>/WinRepair.git
   git push -u origin main
   git push origin --tags
   ```
3. **Релиз:** репозиторий → *Releases* → *Draft a new release* → выберите тег `v1.0.0-rc1` → отметьте **«Set as a pre-release»** (это кандидат в релиз) → в описание вставьте раздел из `CHANGELOG.md` и **SHA-256 архива** → приложите `WinRepair-1.0.0-rc1.zip` (собранный пакет, подписанный). Или командой: `gh release create v1.0.0-rc1 WinRepair.zip --prerelease --notes-file CHANGELOG.md`.
4. Следующая версия: правите `res/version.h` и `CHANGELOG.md` → коммит → `git tag -a v1.0.0 -m "..."` → push → новый Release. Теги всегда `vMAJOR.MINOR.PATCH`.

Правила коммитов, о которых вы просили: каждое логическое изменение — отдельный коммит с префиксом `feat:` / `fix:` / `docs:` / `chore:`; релиз — аннотированный тег. Журнал: `git log --oneline --decorate`.

## 4. Собственный сайт
Минимальная страница продукта (подойдёт GitHub Pages — бесплатно, репозиторий → Settings → Pages; или любой хостинг):
* название, скриншоты, список возможностей, системные требования (Windows 10/11, WinPE, WinRE; x86/x64/ARM64; права администратора);
* кнопка «Скачать» → ссылка на файл в GitHub Releases или на ваш хостинг, рядом — **SHA-256** и инструкция проверки: `certutil -hashfile WinRepair.zip SHA256`;
* страницы: лицензия, политика конфиденциальности (`PRIVACY.md`), контакт/поддержка, история версий;
* HTTPS обязателен (иначе браузеры и антивирусы будут ругаться на загрузку).

**Репутация у антивирусов и SmartScreen** — главная проблема утилит с правами администратора и правкой реестра/BCD:
* подписывайте exe (сертификат подписи кода; облачные сервисы подписи — например, Microsoft Trusted Signing: условия и доступность в вашей стране проверьте на сайте Microsoft);
* не используйте упаковщики (UPX и т.п.);
* при ложном срабатывании отправляйте файл на разбор: Microsoft Security Intelligence (*Submit a file*), а также производителям, чьи антивирусы ругаются; проверка через VirusTotal;
* репутация SmartScreen накапливается со временем и скачиваниями; EV-сертификат даёт её быстрее.

## 5. Другие площадки
| Площадка | Что сделать |
|---|---|
| **GitHub Releases** | Основной источник файлов (см. выше) |
| **winget** | Сделайте Pull Request с манифестом в репозиторий `microsoft/winget-pkgs` (нужен стабильный URL zip и его SHA-256; portable-приложения поддерживаются). Тогда: `winget install WinRepair` |
| **Chocolatey / Scoop** | Пакет/манифест со ссылкой на Release; проверка у них автоматическая |
| **Софт-каталоги** (MajorGeeks, Softpedia, Softonic и др.) | У каждого есть форма «Submit software»; нужны описание, скриншоты, прямая ссылка, лицензия. Требуют чистую проверку на вирусы |
| **Сборки WinPE** (Sergei Strelec и др.) | Включение — только через автора сборки (его форум/раздел): предложите portable-архив с лицензией, подписью и хэшем; у сборок свои форматы плагинов/папка программ |
| **Профильные форумы** (сервисные инженеры, ru-board и т.п.) | Тема с описанием, ссылкой на сайт/Release, историей версий — основной канал в вашей аудитории |
Правило: файл всегда лежит в **одном** официальном месте, остальные площадки ссылаются на него и показывают тот же SHA-256.

## 6. Регистрация продукта в самой программе (ключи) — как это сделать правильно
Утилита работает в WinPE без интернета, поэтому активация по сети не подходит. Рабочая схема — **офлайн-лицензия с цифровой подписью**:
1. У вас есть пара ключей (например, Ed25519). **Закрытый** хранится только у вас (не в git!); **открытый** вшит в exe.
2. Клиент присылает «имя/организацию» (и, если нужно, идентификатор компьютера). Вы создаёте файл `license.lic`: `owner`, `edition`, `expires`, `features` + подпись.
3. Файл кладётся рядом с exe (или в `Data\`). Программа проверяет подпись открытым ключом и показывает в заголовке «Лицензия: <кому>, Pro, до <дата>». Без файла — режим Free.
4. Редакции: **Free** — диагностика и чтение; **Pro** — изменения системы, WinRE, сценарии, офлайн-реестр (разделение — ваше бизнес-решение).
Ограничения, о которых лучше знать: любую офлайн-защиту при желании обходят; цель — честные клиенты и юридическая основа, а не «непробиваемость». Не привязывайте работу к интернету и не блокируйте программу при ошибке лицензии в режиме «только чтение» — инженер у клиента не должен остаться без инструмента.
Это можно реализовать следующим шагом: модуль проверки подписи (в `src/core`, с тестами), утилита генерации лицензий для вас, строка статуса и окно «О программе / Лицензия».

## 7. Порядок действий
1. Решить модель: открытый код / freeware / платная. 2. Заполнить `LICENSE.txt`, `SECURITY.md` (контакт). 3. Собрать, подписать, пройти `docs/RELEASE_CHECKLIST.md`.
4. Залить в GitHub (приватный), создать pre-release `v1.0.0-rc1`, проверить скачивание на чистой машине. 5. Сделать страницу сайта. 6. Отправить в каталоги/winget/форумы.
7. После отзывов — `v1.0.0`, затем ключи, если нужны.
