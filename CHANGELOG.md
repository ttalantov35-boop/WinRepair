## [1.0.4] — 2026-11-21
Крупный релиз: двуязычный интерфейс расшифровок, снятие пароля Windows и менеджер разделов диска. Собрано из рабочих пакетов 005–010.

### Добавлено
- **Снятие пароля и разблокировка учётных записей** — новое окно (вкладки «Обзор» и «Инструменты ремонта»; `src/ui_password.cpp`, `src/modules/sampwd.*`). Для офлайн-Windows из WinPE/WinRE: список локальных учётных записей из SAM (имя, RID, тип, состояние, есть ли пароль, признак учётной записи Microsoft); снятие пароля (вход с пустым паролем), «снять пароль и включить вход» одной кнопкой, включение отключённой записи, разблокировка. Снятие = обнуление длины NT/LM-хеша в значении `V` (Win7–Win11, в т. ч. AES Win10/11); состояние — биты ACB в значении `F`. Перед правкой куст SAM копируется автоматически (откат — «Отменить изменения сеанса»); новый пароль не задаётся и в журнал не пишется; учётные записи Microsoft офлайн не сбрасываются.
- **Менеджер разделов «Разделы диска»** — новое окно (вкладки «Обзор» и «Инструменты ремонта»; `src/ui_partition.cpp`, `src/modules/partition.*`). Обёртка над `diskpart` для работы из WinPE/WinRE над физическими дисками. Листинг дисков и разделов/томов через Windows API (модель, размер, GPT/MBR, шина, серийный номер; номер, смещение, размер, тип EFI/MSR/восстановление/основной, буква, ФС, метка, свободно; показываются свободные области). Операции: создать, удалить, форматировать (NTFS/FAT32/exFAT), назначить/убрать букву, активный раздел (MBR), сжать/разделить, расширить, конвертировать GPT↔MBR. Визуальная полоса-шкала разделов (клик = выбор), крупные шрифты и цвета, правый клик = меню операций, крупный цветной заголовок диска, автообновление списка и строка статуса. Все операции необратимы: крупное предупреждение и подтверждение каждой.
- **Двуязычный интерфейс (RU/EN)** для расшифровок кодов: коды проблем устройств (`devprob.h`), события журналов и коды DISM/SFC (`event_explain.h`), справочник BSOD (`bsod_catalog.h`); двуязычны HTML-отчёт, окно «Справочник кодов BSOD», журнал, мастер «Что случилось?», окна снятия пароля и разделов, а также единицы размера (КБ/МБ/ГБ ↔ KB/MB/GB). Данные-таблицы хранят оба языка; в сохраняемых `.json` диагностические тексты остаются на русском (служебные данные).

- Новое окно «Свой WinPE с WinRepair» вместо общей формы: три пронумерованные цветные панели — «1. Куда записать» (кнопка «Обзор…» — выбор папки/корня флешки), «2. База образа» (переключатели; ADK недоступен, если не установлен), «3. Установочный образ Windows» внизу, две рамки на выбор: «Файл ISO» (кнопка «Обзор…» — окно проводника) и «Диск или флешка с Windows». Выбранная рамка выделена, вторая и вся панель 3 гаснут, когда не нужны; под рамками живая проверка пути (зелёный — подходит, красный — нет). Путь можно набрать или вставить вручную; кавычки из «Копировать как путь» снимаются, апостроф в пути больше не ломает подключение ISO. Последний выбранный ISO запоминается до закрытия программы.
- WinPE из установочного образа: загрузочные файлы носителя (bootmgr, boot\BCD, boot.sdi, efi) берутся из ТОГО ЖЕ установочного образа, что и boot.wim (версии загрузчика и WinPE совпадают, BCD тот, с которым носитель грузится в BIOS и UEFI); иначе — ADK Media, иначе — эта Windows. Образ помечается загружаемым (`/Bootable`), как в носителях Microsoft. Кусты реестра образа читаются/пишутся с правами резервного копирования — ложная тревога «образ не отдаёт файлы (0x5)» и лишняя распаковка/упаковка (≈5 мин) больше не возникают. В конце — самопроверка носителя в журнале (`bcdedit /enum all` по BCD флешки, `Get-WimInfo` по её boot.wim).
- Окно «Свой WinPE с WinRepair»: под полем «Куда записать» — живая подсказка, что выбрано: флешка FAT32 (загрузится и в UEFI, и в BIOS), флешка NTFS/exFAT или GPT (где не загрузится), папка (с неё не загрузиться — нужны доп. шаги), диск с Windows (нельзя). Внизу слева — кнопка «Флешка уже с WinPE? Сделать загрузочной для BIOS…» для флешки, на которую WinPE скопирован вручную (активный раздел + bootsect /nt60, файлы не удаляются). В подтверждении сборки — что будет сделано для BIOS или что делать с папкой.
- BIOS (Legacy) без ручных шагов: после записи WinPE на флешку программа сама делает её раздел активным (diskpart, только для MBR) и записывает загрузочный код BOOTMGR (`bootsect /nt60 X: /mbr`; bootsect.exe берётся из ADK, установочного носителя или с флешки). Только для флешки/USB-диска и никогда — для диска с Windows. Для флешки в GPT — предупреждение, что в BIOS она не загрузится.
- Исправлено: флешка из «авторского» boot.wim в режиме BIOS (Legacy) падала с «\windows\system32\winload.exe 0xc0000225» — в образе не было загрузчика для BIOS. Теперь при сборке проверяются оба загрузчика (winload.exe — BIOS, winload.efi — UEFI) и ядро; недостающий загрузчик добавляется из System32\boot образа или из этой Windows. Результат проверки — в журнале.
- Исправлено (причина найдена по журналу): «авторский» boot.wim сжат LZMS (recovery/solid, как ESD). DISM такой образ подключает, но файлы из него не читаются (0x780), а обслуживание падает с 0xC1510114 — поэтому ни путь X:\, ни реестр не исправлялись, и флешка получала нетронутый образ с путём $windows.~bt. Теперь: образ любой базы всегда перепаковывается в обычное сжатие LZX (`DISM /Export-Image /Compress:max`); если подключённый образ всё равно не отдаёт файлы — запасной путь: распаковка в папку (`/Apply-Image`), правка, упаковка заново (`/Capture-Image`); проверка пути системы честная — если исправить/подтвердить не удалось, сборка останавливается с понятной ошибкой, а не пишет незагружаемую флешку. Распакованные файлы (владелец TrustedInstaller) удаляются в конце через привилегию восстановления.
- Исправлено (второй подход): ошибка «actual SYSTEMROOT … configured one (X:\$windows.~bt\Windows)» оставалась. Теперь, кроме `DISM /Set-TargetPath`, программа сама проходит по реестру образа (SYSTEM, SOFTWARE, DEFAULT) и исправляет все строки с `$windows.~bt` на `X:\…`; журналы транзакций куста (.LOG1/.LOG2) учитываются и очищаются, чтобы при загрузке WinPE правка не откатилась; в конце — проверка `DISM /Get-TargetPath`. Применяется к установочному образу и к вручную указанному winpe.wim.
- ADK WinPE: вариант больше не отключается. ADK ищется и по реестру (KitsRoot10 — если установлен не в Program Files); если не найден — после «Собрать флешку» можно указать winpe.wim вручную (папка Media рядом берётся автоматически).
- Исправлено: WinPE из «авторских» boot.wim не загружался с ошибкой «actual SYSTEMROOT directory (X:\windows) is different from the configured one (X:\$windows.~bt\Windows)». Теперь при сборке: из boot.wim выбирается образ WinPE, а не «Программа установки» (все образы перечисляются в журнале; install.wim/esd отклоняется — это не WinPE); в образе принудительно задаётся путь системы X:\ (`DISM /Set-TargetPath:X:\`); оболочка `Setup\CmdLine` приводится к winpeshl.exe; проверяется наличие winpeshl.exe. Подходит для boot.wim Windows 10 и 11.
- Источник WinPE: кроме .iso, диска и папки можно указать сам файл boot.wim (например, sources\boot.wim распакованного ISO — где бы он ни лежал); в окне вариант «Файл образа» принимает .iso и .wim. Проверка разрядности образа теперь работает и на русской Windows (DISM пишет «Архитектура»). В образ записывается WinRepair.ini с текущим языком — в английском WinPE программа открывается на том же языке, что и сейчас.
- WinPE builder: new base **"Windows install image (ISO or USB stick) — no ADK needed"**. The program takes the clean WinPE (image #1) from `sources\boot.wim` of any Windows ISO/install stick, marks it bootable and adds WinRepair with autostart and System Restore (`rstrui`). The ISO is mounted automatically and dismounted afterwards; the image architecture is checked. The dialog default is ADK if installed, otherwise the install image.
- Docs: `docs/WINPE_USB.*`, `docs/WINRE_MISSING.*` (RU/EN).

- На базе winre.wim файл `winpeshl.ini` уже существует и защищён (0x780), поэтому перезапись молча не срабатывала и WinRepair не выходила первой (оболочку запускает RecEnv). Теперь результат записи winpeshl.ini проверяется и честно сообщается; добавлен запасной `startnet.cmd`. Для ГАРАНТИРОВАННОГО автозапуска первой используйте базу ADK WinPE — там winpeshl.ini создаётся с нуля и WinRepair запускается сразу, без экрана языка и RecEnv. rstrui на базе ADK добавляется впрыском из работающей системы.

## Плитка WinRepair в меню WinRE (свой WinPE на базе winre.wim)
- RecEnv.exe в смонтированном образе оказался недоступен и для перезаписи (0x780), поэтому подмена оболочки убрана. Вместо неё используется штатный механизм Microsoft «свой инструмент в меню WinRE»: в образ добавляются новые файлы `sources\recovery\tools\WinRepair.exe` (с Playbooks и Lang) и `WinREConfig.xml` с `<RecoveryTools>`. После выбора языка WinRepair запускается плиткой в разделе «Поиск и устранение неисправностей», рядом со штатными средствами; RecEnv и реестр образа не изменяются.

## Автозапуск WinRepair в WinPE: прямая перезапись RecEnv.exe
- На Windows 11 26H2 переименование файлов в смонтированном DISM-образе запрещено (0x780) даже после takeown/icacls, поэтому автозапуск через переименование RecEnv.exe не срабатывал. Теперь `sources\recovery\RecEnv.exe` перезаписывается на WinRepair напрямую (перезапись, в отличие от переименования, проходит) — WinRepair запускается первой. Вторая копия `Windows\System32\Recovery\RecEnv.exe` сохраняется для штатного восстановления (кнопка «Выйти в меню WinRE»). Где переименование разрешено — оригинал по-прежнему сохраняется как RecEnvOrig.exe.

## Автозапуск WinRepair в WinPE: обход блокировки RecEnv.exe
- Подмена `RecEnv.exe` в образе срывалась с «Отказано в доступе» (0x5): файлом владеет TrustedInstaller. Теперь перед переименованием выполняется `takeown` + `icacls` (полные права группе «Администраторы», SID S-1-5-32-544 — не зависит от языка Windows), затем повторная попытка. После подмены WinRepair запускается первой, а экран выбора языка RecEnv больше не появляется; штатное меню WinRE открывается кнопкой «Выйти в меню WinRE» (запускает сохранённый `RecEnvOrig.exe`). Проверено: `rstrui /offline` в собранном WinPE работает.

## Свой WinPE: выбор базы образа
- В диалоге сборки флешки появился выбор базы: `winre.wim` этой системы — со встроенным «Восстановлением системы» (rstrui) — или `ADK WinPE` (чистый минимальный образ, rstrui в нём нет). Загрузочные файлы носителя по-прежнему берутся из ADK Media, когда ADK установлен, иначе из работающей Windows.

## Свой WinPE: восстановление системы и кнопка на главном экране
- В собираемый WinPE добавляются `rstrui.exe` и компоненты восстановления системы (srcore, srclient, vssapi, spp, sppc, dsrole и др.) из работающей Windows — только отсутствующие в образе файлы, с проверкой совпадения разрядности. Кнопка «Восстановление системы: rstrui…» в WinPE выполняет откат офлайн (`rstrui /offline:<Windows>=active`).
- Кнопка «Создать загрузочную флешку WinPE с WinRepair…» вынесена на вкладку «Обзор» (главный экран) и подсвечена оранжевым — видна сразу при запуске. Дубль остаётся в окне WinRE.

## Свой загрузочный WinPE с WinRepair
- Новая кнопка в окне WinRE: «Свой WinPE с WinRepair (флешка)…» — собирает независимый загрузочный носитель с автозапуском программы. База — `winpe.wim` из Windows ADK (если установлен; рекомендуется), иначе `winre.wim` текущей системы. Загрузочные файлы (bootmgr, EFI, BCD, boot.sdi) берутся из работающей Windows или из ADK Media — из смонтированного образа ничего не читается, поэтому ограничение 0x780 не мешает. Чистый WinPE выполняет `winpeshl.ini`: wpeinit → WinRepair, автозапуск гарантирован; в Playbooks и Lang рядом с exe тоже попадают в образ. Флешка не форматируется (нужна FAT32), Secure Boot отключать не требуется. Готовый образ нельзя распространять (лицензия Microsoft) — каждый собирает свой одной кнопкой.

## Сборка ARM64 (Windows on ARM / Snapdragon)
- Релиз теперь собирает и публикует `WinRepair_arm64.exe` (workflow Release: кросс-сборка amd64_arm64), CI проверяет ARM64-сборку на каждом коммите. В WinPE/WinRE ARM64-устройств работает только эта сборка — слоя эмуляции x64 там нет. Строка загрузки выбирается как и раньше по прошивке (`winload.efi` на UEFI; все ARM64-устройства — UEFI).

## Исправлен автозапуск в «WinRE + WinRepair»
- Надёжный автозапуск: RecEnv.exe внутри образа подменяется на WinRepair (оригинал сохраняется как RecEnvOrig.exe), поэтому программа стартует первой при любом способе запуска WinRE — даже там, где реестр образа вызывает RecEnv напрямую, а куст SYSTEM не читается из смонтированного WIM (0x780). Кнопка «Выйти в штатное меню WinRE» запускает сохранённый оригинал; строка RecEnv в winpeshl.ini переводится на RecEnvOrig.exe, чтобы не было цикла.
- Куст SYSTEM смонтированного образа теперь правится через временную копию: прямую загрузку куста из WIM система запрещает (ошибка 0x780), из-за чего исправление оболочки пропускалось.
- Загрузчик записи выбирается по прошивке и пишется в журнал («Прошивка: UEFI/BIOS»): на UEFI — `winload.efi` (раньше на живом хранилище могли прописать `winload.exe`, и запись не загружалась).
- Если целевой том зашифрован BitLocker, образ автоматически размещается на незашифрованном томе: загрузчик не умеет читать WIM с зашифрованного диска. Если такого тома нет — понятная ошибка вместо незагружающейся записи.
- В ряде сборок WinRE оболочка задана в реестре образа напрямую (`SYSTEM\Setup\CmdLine` = RecEnv), и `winpeshl.ini` игнорировался: загружалось штатное меню восстановления, а WinRepair приходилось запускать вручную из командной строки. Теперь при создании образа `CmdLine` приводится к `winpeshl.exe`, поэтому первым запускается WinRepair, а после выхода из него — штатное меню WinRE. Прежнее значение пишется в журнал. Образ нужно создать заново.

## Кнопка «Отменить изменения сеанса» и порядок вкладки «Инструменты ремонта»
- Новая зелёная кнопка «Отменить изменения сеанса…» на вкладке «Инструменты ремонта»: показывает всё, что программа изменила в сеансе (по журналу резервных копий — кусты, ветки реестра, BCD, файлы, карантин), и возвращает состояние на начало сеанса. Кусты реестра восстанавливаются копией целиком, живое хранилище BCD — `bcdedit /import`, файлы — обратной копией, карантин — перемещением на место, ветки реестра работающей Windows — `reg import`. Каждый шаг подтверждается, пишется в журнал; текущие файлы сохраняются рядом с расширением `.before_undo`.
- Журнал изменений сеанса `Data\Logs\undo_journal.tsv` переживает перезапуск: если в текущем сеансе изменений не было, предлагается откат прошлого сеанса (например, после перезагрузки из WinPE), пока его копии целы.
- Кнопки вкладки «Инструменты ремонта» выстроены рядами по назначению: два ряда ремонта (оранжевые), затем диагностика (синие) и защита (зелёные) — цвета больше не перемешаны.

## Выбор целевой ОС в окнах инструментов
- Окна «Автозагрузка и службы» и «Установленные приложения» сразу открываются на системе, выбранной в главном окне, и сами сканируют её (раньше — первая в списке и пустая таблица до нажатия «Сканировать»).
- Список систем обновляется при раскрытии, если главное окно пересканировало диски; выбор не сбрасывается.

## Текущая (онлайн) Windows в «Автозагрузке и службах» и «Установленных приложениях»
- В списке «Целевая ОС» этих окон теперь есть и работающая Windows (раньше только офлайн-системы, поэтому на ПК с одним диском C: список был пуст).
- Онлайн: пользовательские кусты — все загруженные профили (HKEY_USERS\\S-1-5-21-…), служб/драйверы — через CurrentControlSet; отключение/удаление/правка работают так же, как офлайн.

## Несколько офлайн-систем (C: и D:)
- Исправлена причина: имена загруженных кустов были одинаковыми для всех Windows (WRO_SYSTEM…), поэтому второй диск показывал данные первого. Теперь имя уникально для тома (WRO_D_SYSTEM, WRO_D_NU_user…), при смене файла куст перезагружается.
- Реестр: дерево по системам («D:\ … [офлайн]» → кусты), адреса в виде D:\SYSTEM\ControlSet001, меню Файл: загрузить/выгрузить диск, куст из файла, выгрузить выбранный/всё; выбранная в главном окне система загружается автоматически; резервные копии по тому реального куста.
- Автозагрузка и Установленные приложения: пересканирование сразу при смене диска в списке.
